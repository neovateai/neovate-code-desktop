# Internationalization with react-i18next

**Date:** 2026-01-27

## Context

Neovate Code Desktop needs internationalization support to serve international users. The application currently has ~200 hardcoded English strings across ~100 React components, with no i18n infrastructure in place. A "Language" preference field exists in settings (English, Chinese, Japanese, Spanish) but is non-functional.

**Goals:**
- Support multiple languages for international users
- Initial languages: English + Chinese (Simplified)
- Auto-detect system locale with user override
- UI strings only (date/number formatting deferred)

## Discussion

### Library Selection

Three approaches were evaluated:

| Library | Pros | Cons |
|---------|------|------|
| **react-i18next** | Industry standard, clean hooks API, built-in detection, large ecosystem | Slightly larger bundle (~15kb) |
| react-intl | Strong ICU format support, good TypeScript | Overkill for simple strings, steeper learning curve |
| Custom solution | Zero dependencies, full control | Reinvents the wheel, no detection/pluralization |

**Decision:** react-i18next — mature, battle-tested, excellent DX with `useTranslation` hook.

### Translation File Structure

Three structures were considered:

1. **Multiple files by feature** (`locales/en/settings.json`, `locales/en/chat.json`)
   - Good for lazy-loading, but adds complexity

2. **Single flat file** (`locales/en.json` with `settings_providers_api_key`)
   - Simple but unwieldy at 200+ strings

3. **Single nested file** (`locales/en.json` with `settings.providers.apiKey`)
   - One file per language, organized hierarchically, translator-friendly

**Decision:** Single nested file per language — sweet spot for ~200 strings.

### Language Detection

**Decision:** Auto-detect from system locale first, allow user override in Settings. The existing Language preference will be wired to actually switch languages.

## Approach

Implement i18n using react-i18next with this architecture:

```
src/renderer/
  locales/
    en.json          # English (default)
    zh-CN.json       # Chinese Simplified
  i18n.ts            # i18next configuration
```

**Key naming convention:** Dot-notation by feature
- `common.save`, `common.cancel`, `common.loading`
- `settings.providers.apiKey`, `settings.appearance.theme`
- `chat.input.placeholder`, `chat.messages.error`

**Usage pattern:**
```tsx
import { useTranslation } from 'react-i18next';

function SaveButton() {
  const { t } = useTranslation();
  return <button>{t('common.save')}</button>;
}
```

## Architecture

### Dependencies

```json
{
  "i18next": "^23.x",
  "react-i18next": "^14.x",
  "i18next-browser-languagedetector": "^7.x"
}
```

### Configuration (src/renderer/i18n.ts)

```typescript
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';
import en from './locales/en.json';
import zhCN from './locales/zh-CN.json';

i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources: {
      en: { translation: en },
      'zh-CN': { translation: zhCN },
    },
    fallbackLng: 'en',
    interpolation: { escapeValue: false },
  });

export default i18n;
```

## Troubleshooting Notes (January 28, 2026)

### Symptom: UI stays in English after switching to zh-CN

**Root cause**
- `i18next` renders based on `resolvedLanguage`.
- With strict `supportedLngs`, `resolvedLanguage` can remain `en` even when `i18n.language` shows `zh-CN`, causing all `t()` calls to fall back to English.

**Fix**
- Keep `normalizeLocale()` to map language codes to the supported set.
- Do **not** set `supportedLngs`/`nonExplicitSupportedLngs` for the current two-language setup; this prevents `resolvedLanguage` from sticking to `en` due to detection mismatch.

**Checklist**
- `t('settings.appearance.title')` should change when switching languages.
- If it doesn't, check `resolvedLanguage` at runtime and ensure it matches `i18n.language`.

## Sync + Persistence (Lobe-style, Desktop)

### What we do
- **Single i18n instance** created in `src/renderer/i18n.ts`, initialized before store hydration.
- **Store is the source of truth** for UI locale (`uiLocale`), persisted via the existing Electron store.
- **Language switching** routes through a helper:
  - `applyUILocale()` normalizes locale, calls `changeLanguage()`, and updates `<html lang>`.
  - `setUiLocale()` in `src/renderer/store/slices/desktopSettings.ts` invokes `applyUILocale()`.
- **Hydration** in `src/renderer/main.tsx` restores persisted `uiLocale` and applies it before the first render.

### What we intentionally skip
- **Namespaces**: not needed for two locales and a single UI bundle.
- **SSR sync**: not applicable (desktop, no SSR).
- **Cookie persistence**: Lobe uses cookies for the web; we persist to the Electron store instead.

### Why this mirrors Lobe
- Lobe’s `switchLang()` centrally changes language and updates HTML lang.
- Lobe’s `switchLocale()` stores the locale in a global store and persists it.
- We mirror that flow using `setUiLocale()` + `applyUILocale()` + the Electron store.
